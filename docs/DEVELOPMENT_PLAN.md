# 开发计划

## 1. 执行策略

采用垂直切片、分阶段交付。先建立最小可运行骨架，再交付一个完整学习闭环；不要一次性生成整个产品。

开发前先明确知识数据来源与验证流程。界面可以使用标注为 mock 的数据进行布局开发，但 mock 数据不得伪装成正确的五笔知识。

## 2. 优先级

- **P0**：MVP 必需，必须完成并验收。
- **P1**：提升体验，可在核心闭环后完成。
- **P2**：后续版本。

## 3. Phase 0：知识数据准备

### 任务

- 确定可使用的 86 版资料来源及许可/引用方式。
- 设计字根、键位、编码、拆字和课程数据 Schema。
- 建立数据校验脚本与来源记录格式。
- 整理第一批教学所需数据，并进行人工复核。
- 对无法核实的数据标记待核验，不进入正式课程。

### 验收

- 每条正式知识数据都能追溯来源。
- 字根键位、编码类型和拆字步骤通过校验。
- 数据明确标注 86 版，不混入其他版本。
- 数据缺失或冲突会导致校验失败或产生明确报告。

## 4. Phase 1：项目基础

### 任务

- 初始化 Vite + React + TypeScript strict。
- 配置 Tailwind CSS 和基础 UI 组件。
- 配置路由和全局布局。
- 接入 Zustand 和 Dexie.js。
- 建立目录结构、代码规范和测试框架。
- 实现基础错误处理和空状态。

### 验收

- 本地可启动、可构建。
- 路由可访问，基础布局可用。
- IndexedDB 可创建、读写和升级。
- Vitest 可运行，CI/本地检查命令明确。

## 5. Phase 2：学习首页与课程框架

### 任务

- 首页学习进度概览。
- 课程目录与课程详情框架。
- 继续学习入口。
- 课程状态与通过标准服务。
- 基础响应式布局。

### 验收

- 用户可浏览课程并进入课程。
- 课程状态由统一业务逻辑计算。
- 无学习记录时显示清晰的新手引导。

## 6. Phase 3：键盘与字根学习

### 任务

- 实现 86 版键盘组件与五区高亮。
- 键位详情和字根列表。
- 字根卡片与助记内容。
- 看字根找键、看键找字根、混合测验。
- 物理键盘输入处理。
- 练习反馈与答题记录。

### 验收

- 键盘布局与字根映射通过数据测试。
- 物理键盘输入不会错误依赖中文输入法上屏。
- 输入法组合输入、焦点和快捷键处理符合设计。
- 字根练习反馈准确且可复习。

## 7. Phase 4：拆字与基础编码

### 任务

- 汉字结构与拆分步骤展示。
- 拆字规则说明。
- 键名字根课程。
- 成字字根课程。
- 基础单字编码练习。
- 一级简码课程与练习。
- 末笔字型识别码等规则的分步解释。

### 验收

- 每个教学示例都来自已核验的数据集。
- 拆分步骤、字根序列和编码结果一致。
- 简码与全码明确区分。
- 关键编码判定逻辑有单元测试。

## 8. Phase 5：学习闭环

### 任务

- 课程完成与掌握状态更新。
- 错题记录、筛选和复习。
- 学习报告与知识点掌握情况。
- IndexedDB 数据恢复。
- 学习数据导入和导出。

### 验收

- 练习结果正确更新课程进度。
- 错题可查看、可重新练习，历史答题不丢失。
- 刷新后状态恢复。
- 导入导出往返测试通过。

## 9. Phase 6：质量与发布准备

### 任务

- 完成关键路径 E2E 测试。
- 检查键盘可操作性、焦点管理和响应式布局。
- 优化性能、错误提示和空状态。
- 完善 README、使用说明和数据来源说明。
- 检查依赖体积与浏览器兼容性。

### 验收

- 关键 E2E 路径稳定通过。
- 类型检查、单测、构建通过。
- 没有未标注的 mock 知识数据进入生产构建。
- 本地数据导入导出和刷新恢复正常。

## 10. 建议开发顺序

每个阶段以可运行、可验证为目标。推荐先完成一个端到端的小闭环：

1. 展示一组经过核验的字根。
2. 用户完成一次字根识别练习。
3. 展示正确/错误反馈。
4. 记录本次答题。
5. 刷新后仍能看到进度。

再逐步扩展到拆字、编码、错题和报告。

## 11. AI Agent 协作规范

将本节作为代码代理执行任务时的默认约束：

1. **先读后改**：先检查项目结构、现有实现和相关文档，不得无条件重建项目。
2. **小步交付**：每次只处理一个明确功能或一组紧密相关任务。
3. **遵守既定技术栈**：未经讨论，不擅自更换框架或增加依赖。
4. **领域逻辑独立**：编码、拆字、键盘判定和学习规则不得写进 UI 组件。
5. **知识数据不猜**：不得凭模型记忆补齐字根表、编码、简码或拆字步骤；不确定就标记待核验。
6. **测试随代码交付**：核心领域逻辑必须有测试；修复缺陷时增加回归测试。
7. **控制修改范围**：避免无关重构、格式化整个仓库或删除现有功能。
8. **完成后验证**：运行类型检查、相关测试和生产构建；若无法运行，明确说明原因。
9. **同步文档**：数据结构、行为或架构发生变化时更新对应文档。
10. **清楚汇报**：说明修改文件、实现内容、测试命令及结果、遗留问题。

## 12. MVP 完成定义（Definition of Done）

- 产品需求中的 P0 功能均已实现。
- 核心知识数据来源可追溯且校验通过。
- 领域逻辑测试、集成测试和关键 E2E 测试通过。
- TypeScript strict 检查和生产构建通过。
- 本地学习数据刷新可恢复，导入导出可用。
- 文档与实际实现一致。
